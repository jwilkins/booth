Speed · measured, not claimed

Adding one track
should take seconds.
Here is how many.

The number that decides whether a night goes well is not how long the first write of a drive takes — that happens at home, once — but how long adding a track to it takes at five to midnight. rekordbox users report hours. These are Booth's figures, taken by the test suite and republished with every measurement, so the claim is a number with a date on it.

Preparing is decoding a record and listening to it — tempo, grid, key, phrases, cues, waveforms — and it scales with how long the records are. The records here are short on purpose, so that the drive is what is being timed; a real record takes longer to listen to and exactly as long to put on the stick. Databases alone is a write that changes nothing but the two databases: a playlist reordered, a track taken off. Add one track is a full drive carried as it is, one file prepared, both databases rebuilt and read back.

The medium these were taken on is named above the table. A runner's disk is not a USB stick, and a stick's small-file write speed is the thing rekordbox's own forum blames most. The figure that counts is the one taken on a real stick — here is how to take it.

02 — Versus rekordbox

The same job, as its own users describe it

rekordbox's Sync overwrites the whole data set on the stick every time, so adding one track costs what writing the drive cost. These are not benchmarks of rekordbox — nobody publishes those — but what DJs reported on AlphaTheta's own forum, with the threads linked so the comparison can be checked.

rekordbox, as reported
4 hours to Sync after adding one track to a playlist — rekordbox 7.2.7, macOS, February 2026. The reply explains that Sync rewrites everything.
Booth, measured
… to add one track to a drive of … tracks, both databases rebuilt and read back, on the medium named above.
rekordbox, as reported
~1 hour to export a few hundred tracks, and nearly 30 minutes to import a few hot cues back off the stick — October 2026, the same complaint as a thread that ran from 2017 to 2021.
Booth, measured
… to read a drive of … tracks back in full: both databases, every analysis file, every track's cues.

Two things make the difference, and neither is clever. A second write carries every row the drive already has and prepares only what changed, so the cost of adding a track is the cost of one track. And both databases are built from one description of the drive and written in one pass, so there is no reconciliation step and nothing to re-walk — the read-back afterwards is a check, not a repair.

03 — How it is measured

By the test suite, in release, with the clock on the outside

The measurement is a test — proto/musicai/tests/speed.rs — that builds drives of several sizes from synthetic records, times each phase with a wall clock around the same calls the window makes, and writes what it saw to speed.json. This page reads that file; nothing on it is typed in by hand.

A smaller version of the same test runs with every build and makes the structural claim as a ratio rather than a budget: adding one track must cost less than half of writing the drive, and so must rewriting the databases alone. A ratio holds on a laptop and on a loaded runner alike, and a regression that made the second write rewrite everything would still fail it.

The speed workflow takes the published measurement on a GitHub-hosted runner whenever the code that writes a drive changes, and once a week so the date never goes stale. Its disk is a fast one and not a stick, which is why the medium is printed beside the numbers.

04 — On your own stick

The number that counts is yours

Point the same test at a mounted drive and it measures that drive. The result is the same file this page reads, so committing it publishes it.

scripts/speed.sh /Volumes/STICK          # macOS
scripts/speed.sh /media/$USER/STICK      # Linux
BOOTH_SPEED_SIZES=50,500 scripts/speed.sh /Volumes/STICK

It is a release build and several minutes of writing drives. Everything it writes goes under a booth-speed-N folder on the drive and is removed afterwards; nothing already on the stick is touched.
